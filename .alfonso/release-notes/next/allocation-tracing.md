- The `aft` binary now names the operation behind large heap use in its log, for diagnosing short multi-gigabyte memory bursts. Any single allocation or reallocation of 64 MiB or more writes one WARN line (`large allocation 512 MiB realloc from 256 MiB thread=aft-subc-runtime op=frame_encode root=<repo> build_id=<uuid> frames=aft+0x…`). When one operation's live heap bytes cross 512 MiB through many smaller allocations, it writes `allocation burst: op=<label> …`, and when they fall back below half of that, `allocation burst ended: op=<label> peak … over …s`. The labels are each tool call (`tool:<name>`), `index_build`, `callgraph_start`, `callgraph_refresh`, `segment_fold`, `meaning_fill`, `symbol_prewarm`, `remote_input_capture`, `frame_encode` and `census`. Call-graph resolver pool work carries the label of the operation that started it. The uncapped memory census adds `allocation_labels`: the five operations with the highest live-byte marks since the previous census. The tracer's logger writes at most 20 lines a minute. Memory that C libraries take from `malloc` directly (SQLite, tree-sitter, ONNX Runtime) is not seen.
- Each frame is printed as an image and an offset because the shipped binary is stripped. To name the frames, take the binary's dSYM (macOS) or debug file (Linux) with the `build_id` on the line: `aft profile` keeps them under the AFT storage root's `dsym/<build_id>`. Then run `atos -o <aft.dSYM>/Contents/Resources/DWARF/aft -arch arm64 -offset 0x1a2b3c …` on macOS, or `addr2line -C -f -p -e <aft.debug> 0x1a2b3c …` on Linux, with the `aft+0x…` offsets from the line.
