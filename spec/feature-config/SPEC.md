# Feature-based config and setup wizard: approved spec
Folded spec from campaign ct_00000000-0000-4018-98d8-c19acf5d2ef8 (2026-09-23), with the owner's chair rulings applied. Slice 1 evidence lives beside this file.

## Intent

A new AFT install should get AFT's main features without editing config. Today it doesn't: `tool_surface: "recommended"` leaves out `aft_callgraph`, and `search_index: false` and `semantic_search: false` leave out `grep`/`glob` hoisting and `aft_search` (verified in `packages/opencode-plugin/src/tool-registration.ts` lines 132-151 and `docs/config.md`). This change replaces surface levels with one rule: **a tool is on unless it is in `disabled_tools`**. The background indexes (trigram, semantic, callgraph) become first-class features that build when turned on, and `aft setup` gains a checkbox wizard that writes the choices and can be rerun to reconfigure. `tool_surface` and `hoist_builtin_tools` are removed outright: AFT either takes over a tool or the tool is disabled; there are no `aft_read`/`aft_write`/`aft_edit` fallback names. The wizard should be built so the future `ck setup` can reuse its feature list rather than reimplement it.

## Constraints

### Fixed scope and registration

- Delete `tool_surface`, `hoist_builtin_tools` and `RawToolSurface`; there are no surface levels. Host tools register as `read`, `write`, `edit`, `apply_patch`, `grep`, `glob`, `bash`, or not at all. Remove duplicate prefixed registrations.
- A tool registers exactly when its canonical name is absent from resolved `disabled_tools`. Index state, backend presence and capability settings never remove registration. Rust `aft_search_registered` and its documentation denote registration only, independent of indexes and backend presence.
- Footer generation receives an engine-internal `SearchLaneReadiness { trigram: boolean, semantic: boolean }` parameter named `search_lane_readiness`, computed from current engine index status: a lane is true only when ready; unobserved lanes are false. This is a runtime function parameter, never plugin-supplied configuration. Footer call sites obtain it from the engine status provider; plugins obtain readiness only in the existing runtime status payload. Exclude this carrier and lane fields from config schemas, generated config artifacts, resolved configuration and parity snapshots. Recommend `aft_search` only when registered and at least one lane is ready; otherwise name `grep`.
- Absent user-base `disabled_tools` defaults to `["aft_move","aft_delete"]`, subject to explicit legacy-surface migration below. An explicit list replaces the default: `[]` enables both; `["aft_search"]` disables only search. `aft_import` remains default on. No new tool-enable key is introduced.
- Preserve raw list presence per tier/harness block as `string[] | undefined` in TS and `Option<Vec<String>>` in Rust through translation, merging and wire handling. Apply the absent-base default exactly once at user-base resolution, before merging. A resolved sender always supplies the resulting list, including `[]`; merging and serialization must not drop empty lists. Do not reapply defaults after merging.
- Engine configure is a resolved-config protocol, not a raw user-config loader. Before deserializing into any defaulted engine structure, validate that `disabled_tools`, `indexes`, and each of `indexes.trigram`, `indexes.semantic`, `indexes.callgraph` are present with their canonical types. Missing fields reject with `invalid_resolved_config:missing:<path>`; wrong types reject with `invalid_resolved_config:type:<path>`. Report the missing container rather than its children when the container is absent; report multiple errors in sorted path order. Reject the entire candidate before publication or index work; retain last-good state on reload. In particular, absent disables must never become an implicit `[]`, and missing index leaves must never acquire historical defaults. Raw file parsing still permits omission under the user-base rules.
- Inventoried bash companions are independently registered by name. Disabling the `bash` tool does not unregister companions. Missing runtime prerequisites return named unavailable results.
- Preserve semantic backend, LSP, formatter, sandbox, bash sub-features, inspect and backup runtime settings. `backup.enabled:false`, `inspect.enabled:false` and a false bash runtime gate cease to be canonical registration predicates; calls requiring them report `backup_disabled`, `inspect_disabled` or `bash_disabled`. Missing semantic backend affects only that lane. Legacy top-level `enabled:false` migrates to explicit disables; no whole-plugin registration exception survives.
- The canonical bash runtime gate is `bash.enabled:boolean`, default true, represented by Rust `BashConfig.enabled: bool` and the Zod bash-object `enabled` leaf. Continue accepting the existing raw `bash:true|false|{...}` forms: booleans normalize to that enabled value, an object without `enabled` defaults true, and resolved config/wire serialize an object containing `enabled` and the existing normalized sub-features. All bash-execution operations, including independently registered companions, check this resolved gate and return `bash_disabled` when false; disabling only the tool name `bash` does not turn the runtime gate off. During the migration window, raw `bash:false` or explicit `bash.enabled:false` also generates the frozen historical bash-gate disable set. After the window both remain accepted runtime-only settings. Slice 1 freezes the exact historical generated names, including any affected companions; runtime blocking does not enlarge that registration set.
- On all four registration adapters (OpenCode V1, OpenCode V2, Pi, OMP), requested `edit_mode:"hashline"` is effective only when both canonical read and edit survive resolved disables. Otherwise emit exactly one configure-time warning per load operation: `hashline_read_disabled` or `hashline_edit_disabled`, with read taking precedence. Use `configure_warnings_delivery` with adapter-log fallback, or CLI stderr. Surviving slots use ordinary non-hashline behavior. Do not unregister another tool or override a disable; this is neither a per-call error nor a new catalog row.
- Unknown disabled names remain inert and preserved. Each plugin/CLI load operation emits one aggregated `unknown_disabled_tools` warning listing distinct unknown names in sorted order through the notice channels below; it is not persistently suppressed. Setup load/write is one operation and must not duplicate it. Known names come from the complete canonical inventory, not the enabled subset.

### Setup and reusable plan contract

The binary owns the catalog. `aft setup --plan` emits `{plan_version:1,features:[]}`. Each feature contains:

- `id:string` (canonical tool name or boolean path), `kind:"tool"|"index"|"capability"`, `group:string`, `order:integer`, `label:string`, `description:string`;
- `binding:{path:string,tool_name:string|null}`: tools bind to disabled_tools by name, others to their boolean path;
- `default:boolean`, `configured:boolean`, `source:"default"|"config"`, `proposed:boolean`, `effective:"off"|"building"|"ready"|"unavailable"`, `reason:string|null`;
- `available:boolean`, `unavailable_reason:string|null`, `cost_note:string|null`, `prerequisites:string[]` referencing feature IDs, describing runtime dependencies, never registration gates.

#### Shared derivation and availability matrix

Apply supplied ruling 5.E identically in plan, doctor and exposed consumer feature-status objects. Resolve tiers, trust and capability implications before choosing effective status. `configured` and `source` describe the base-user choice only, not final tier resolution. `reason` explains effective derivation independently of failure; `unavailable_reason` alone gives the unavailable prerequisite/cause. Although the v1 field permits null, catalog rows use these literal derivation strings, including tool rows:

- `"default"` when the effective choice comes from built-in defaults.
- `"configured"` when it comes from explicit accepted configuration, including translated values and applicable user-harness/project overrides. For tools, a present base disable list is a configured membership choice for every known tool; an accepted later disable makes its affected tool configured. For index AND resolution, any accepted explicit false responsible for off makes the derivation configured; otherwise use the winning explicit user value or applicable explicit project value, if any. Ignored protected/project re-enable attempts do not change provenance.
- `"implied by github.write"` when read is on because write is on while independently resolved read would be off. This takes precedence over default/configured, including explicit read false. It is retained even if a runtime prerequisite is unavailable. Independently enabled read retains its own default/configured derivation.

| Feature state | `effective` | `available` | `reason` | `unavailable_reason` |
| --- | --- | --- | --- | --- |
| Resolved-off index/capability | `off` | true | Derivation above | null, regardless of unsupported backend or absent observation |
| Enabled observed index | `ready` or `building` | true | Derivation above | null |
| Enabled unsupported/unobserved index | `unavailable` | false | Derivation above | Named cause, including `runtime_not_observed` |
| Enabled usable capability | `ready` | true | Derivation above | null |
| Enabled blocked capability | `unavailable` | false | Derivation above | Named runtime cause; capabilities never report building |
| Disabled tool | `off` | true | Derivation above | null |
| Registered usable tool | `ready` | true | Derivation above | null |
| Registered runtime-blocked tool | `ready` | false | Derivation above | Named prerequisite cause; registration does not change |

Available for an off feature means no active request is blocked, not a promise that enabling will succeed. A default-on unobserved index therefore has `reason:"default"` and `unavailable_reason:"runtime_not_observed"`; configured-off unsupported semantic has `reason:"configured"` and `unavailable_reason:null`. A write-implied read row with false base read and no blocking prerequisite is exactly `configured:false`, `effective:ready`, `available:true`, `reason:"implied by github.write"`, `unavailable_reason:null`. If a runtime prerequisite is missing, keep that reason and place only the failure cause in `unavailable_reason`, with effective unavailable/available false. Availability failure never overwrites derivation. Effective write must not coexist with effective read off.

IDs/order are stable within v1. Compare emitted tuples with `spec/feature-config/catalog.json`, not independently invented snapshots.
