## Verdict

The loader, Effect entry precedence, typed RPC, tool replacement, tool execute contract, interruption ordering, path rendering, and the Effect dependency are unchanged from 2.0.3 to 2.0.11. The plugin Effect context lost `permission.rules` and split `catalog` into `provider` and `model`; `SessionDomain` renamed `rename` to `update`. None of those touch a surface AFT calls.

On permissions, two facts hold at once and must not be collapsed into each other.

The first is about the GA contract: a server plugin is handed twenty-five separate per-domain facades and no client, and its permission facade is `Pick<PermissionApi, "list" | "get" | "reply">`, which excludes `create`. `permission.create` does exist on the full `@opencode/client` with an unchanged request shape, but that client is given to the TUI context, not to the server. Points 2 and 4 record both halves.

The second is about our code, and it is the one that decides the matrix: AFT never reaches the GA contract at all. `hoistedV2ToolConsumers` probes `"client" in host` against a context that has no `client` member and never had one, installs no consumer, and every ask is refused by our own error string before any host interaction occurs. Nothing upstream is asked for and denied. The failing mechanism is inside the plugin.

## Relied-on contract diff

1. **Plugin Effect context permission domain — changed; `rules` removed.** At 2.0.3 the domain was `Pick<PermissionApi<unknown>, "list" | "get" | "reply" | "rules"> & { hook }`; at 2.0.11 it is `Pick<PermissionApi<unknown>, "list" | "get" | "reply"> & { hook }`. The server runtime that builds the context implements exactly `hook`, `list`, `get`, `reply`. Citations: `@opencode/plugin@2.0.11/dist/effect/permission.d.ts:19-21` against `@opencode/plugin@2.0.3/dist/effect/permission.d.ts:19-21`; `@opencode/core@2.0.11/dist/chunks/snapshot-qgzk9bq2.js:412-417` against `@opencode/core@2.0.3/dist/chunks/mime-pe4b2cf4.js:403-409`. The same narrowing appears on the promise adapter at `@opencode/plugin@2.0.11/dist/promise/permission.d.ts:19`. Classification: **changed**. AFT calls none of these four members, so the removal has no effect on AFT.

2. **Client `permission.create` — preserved on the full client, and not reachable from a server plugin.** The client's permission domain carries `create(input: PermissionCreateInput) => Promise<{ id, effect }>` in both versions. `PermissionCreateInput` is a flattened struct of the path parameter plus the request body: `sessionID` (required), `id?`, `action` (required), `resources` (required), `save?`, `metadata?`, `source?` (`{type:"tool", messageID, id}`), `agent?`. The two declarations are field-for-field and type-for-type identical; only their line offsets moved. `PermissionEffect` is `"allow" | "deny" | "ask"` in both. Citations: `@opencode/client@2.0.11/dist/promise/client.d.ts:157-160` against `@opencode/client@2.0.3/dist/promise/client.d.ts:168-171`; `@opencode/client@2.0.11/dist/promise/generated/types.d.ts:7506-7615` against `@opencode/client@2.0.3/dist/promise/generated/types.d.ts:7666-7775`; `@opencode/client@2.0.11/dist/promise/generated/types.d.ts:35` against `@opencode/client@2.0.3/dist/promise/generated/types.d.ts:18`. AFT's request sends `sessionID`, `action`, `resources`, `save`, `metadata`, `source` (`packages/opencode-plugin/src/permissions/v2.ts:148-155`), every one of which is an accepted field of that input at both versions. Classification: **preserved on the client package**. This point says nothing about reachability; point 4 is what decides that, and it decides it against us.

3. **Permission creation over HTTP — preserved.** The protocol group publishes `session.permission.create` as `POST /api/session/:sessionID/permission` with body `{id?, action, resources, save?, metadata?, source?, agent?}` and success `{data: {id, effect: "allow"|"deny"|"ask"}}`, in both versions. 2.0.11 additionally requires the session-location middleware on that endpoint, where 2.0.3 declared none; that is server-side location resolution and does not change the request a caller sends. Citations: `@opencode/protocol@2.0.11/dist/groups/permission.d.ts` (`makePermissionGroup`, `session.permission.create` endpoint declaration) against `@opencode/protocol@2.0.3/dist/groups/permission.d.ts` (same endpoint). The underlying service still exposes `ask`, `assert`, `reply`, `get`, `forSession`, `list`, `close` at `@opencode/core@2.0.11/dist/chunks/snapshot-67b7pecv.js:300`. Classification: **preserved**.

4. **The object a server plugin receives — twenty-five domain facades and no client, in both versions. This is the decisive point.** The Effect `Context` handed to a server plugin has members `app`, `location`, `options`, `agent`, `aisdk`, `command`, `event`, `experimental`, `integration`, `mcp`, `model`, `generate`, `permission`, `plugin`, `provider`, `reference`, `rpc`, `session`, `shell`, `skill`, `storage`, `tool`, `vcs`, `websearch`, `worktree`. There is no `client`, neither a full one nor a narrowed one: the context is not a client with members removed, it is a set of separate per-domain facades, each declared as a `Pick<...Api, ...>` sliced from the client's API types. The permission facade is `Pick<PermissionApi<unknown>, "list" | "get" | "reply">` at 2.0.11 and the same plus `"rules"` at 2.0.3; `create` is excluded from both. The runtime object that populates the context has exactly those top-level keys. The TUI plugin context, by contrast, does carry `readonly client: OpenCodeClient` — the full promise client from point 2 — but that runs in the TUI process, not in the server where AFT's tools execute. Citations: `@opencode/plugin@2.0.11/dist/effect/plugin.d.ts:25-53` (verified against the installed pin, not only the tarball) against `@opencode/plugin@2.0.3/dist/effect/plugin.d.ts:24-51`; `@opencode/plugin@2.0.11/dist/effect/permission.d.ts:19-21`; `@opencode/core@2.0.11/dist/chunks/snapshot-qgzk9bq2.js:197-503` against `@opencode/core@2.0.3/dist/chunks/mime-pe4b2cf4.js:204-492`; `@opencode/plugin@2.0.11/dist/tui/context.d.ts:449` against `@opencode/plugin@2.0.3/dist/tui/context.d.ts:446`.

   AFT's server entry passes that context straight into the permission binder (`packages/opencode-plugin/src/entry/server-runtime.mjs:31`). `host.client` is therefore `undefined`, the guard `if (!("client" in host)) return {}` short-circuits (`packages/opencode-plugin/src/tools/hoisted/v2.ts:19-24`), no `requestPermission` consumer is installed, and every ask rejects. The harness captured that refusal at 2.0.3 (`tests/docker/opencode2/contract/probe/bash-t1-permission-refusal.txt`), including the plugin's own log of the context keys with no `client` among them, and the pre-guard form of the same defect as a `TypeError` on `host.client.event`.

   Classification: **preserved absence on the server context**. `V2PermissionHostContext` describes an object GA does not hand a server plugin. What this point does *not* establish is that GA offers a plugin no way at all to initiate a permission decision: the context does expose `permission.hook`, and whether that or some other supported route can carry AFT's requirement is an open design question owned by a separate task, not something this audit settles. What is settled is narrower and sufficient for the matrix: our probe tests a member that has never existed on this contract, so the refusal our tools emit is produced by our own code before any host interaction.

5. **Client event subscription shape — preserved, and AFT's declared shape does not match it at either version.** `client.event.subscribe(options?)` returns `AsyncIterable<V2Event>` directly in both versions. AFT declares the member as `subscribe(): Promise<{ stream: AsyncIterable<unknown> }>` and reads `.stream` off the awaited value. Against a real client that read yields `undefined`. Citations: `@opencode/client@2.0.11/dist/promise/client.d.ts:10-12` against `@opencode/client@2.0.3/dist/promise/client.d.ts:10-12`; AFT's declaration at `packages/opencode-plugin/src/permissions/v2.ts:42-45,142-143`. Classification: **preserved on the host side**; the mismatch is AFT's and predates this pin move. It matters because it is the second defect on the same path as point 4: supplying a client without fixing this would substitute one dereference failure for another.

6. **Loader and Effect entry precedence — preserved, byte-identical.** `Host.resolve` still tries `server` then the package root for the server entry, `tui` for TUI, and `rpc` for RPC, swallowing only the six resolution error codes. The core module decoder still accepts default `{id, effect}` or `{id, setup}`, selects the Effect arm by `"effect" in value`, uses `entrypoints.server` as the entry, and derives `features.tui` / `features.rpc` purely from resolvability. `dist/host.js` and the decoder region are textually identical between the two versions. Citations: `@opencode/plugin@2.0.11/dist/host.js:4-33` against `@opencode/plugin@2.0.3/dist/host.js:4-33`; `@opencode/core@2.0.11/dist/chunks/snapshot-rnmzpqyz.js:54-65,72-101` against `@opencode/core@2.0.3/dist/chunks/mime-771dt0vh.js:54-65,72-101`. Classification: **preserved**.

7. **Typed RPC — preserved.** `RpcDomain` still extends `RpcApi` and adds `register(definition, handlers)`; `effect/rpc.d.ts` is identical between the versions. The server context still installs it as the RPC client with `register` merged on. A resolvable `./rpc` subpath still only marks `features.rpc`. AFT keeps registering `getStatus` from the server Effect and still publishes no `./rpc` export. Citations: `@opencode/plugin@2.0.11/dist/effect/rpc.d.ts:6-19` against `@opencode/plugin@2.0.3/dist/effect/rpc.d.ts:6-19`; `@opencode/core@2.0.11/dist/chunks/snapshot-qgzk9bq2.js:200` against `@opencode/core@2.0.3/dist/chunks/mime-pe4b2cf4.js:207`; `@opencode/core@2.0.11/dist/chunks/snapshot-rnmzpqyz.js:91-94`. 8. **Interruption — ordering preserved; one optional query parameter renamed.** The runner still interrupts tool fibers when the provider stream is interrupted, awaits all tool fibers, re-interrupts if the join fails, then records unsettled-tool and assistant failures in that order. The HTTP control is still `POST /api/session/:sessionID/interrupt` returning `{interrupted: boolean}` with `false` as the idle no-op. Two things moved: the optional query parameter is `resume` at 2.0.11 where it was `continue` at 2.0.3, and the OpenAPI identifier dropped its `v2.` prefix. ## What this changes for the matrix

The thirty `expected_fail:https://github.com/anomalyco/opencode/issues/37164` rows lose that label and become `applicable`.

The reason is point 4's second half, not point 2. Upstream 37164 asks the host to offer a permission-request capability inside the V1-style `tool.execute.before` hook. That is not what happens on a GA host: AFT does not reach a host API and get refused, it short-circuits inside `hoistedV2ToolConsumers` on a membership test for a key the GA contract does not define, and emits its own refusal string. An upstream issue cannot be the justification for a failure that occurs before the host is consulted, whatever that issue says about the host.

`applicable` is the label the matrix's own rule leaves: `expected_fail` has to earn its place and this one has not, and `n/a` is false because the operation is real and attempted. It is not a claim that these rows pass — none of them does.

One dependency is explicit and unresolved. Whether a supported GA mechanism exists for a plugin to initiate a permission decision — `permission.hook`, or another route to the endpoint in point 3 — is being determined by the task that owns the fix. If the answer turns out to be that no such mechanism exists, these rows may belong back under `expected_fail` with an issue that actually describes the gap. They should not return to 37164, which describes a different mechanism on a different hook.

Upstream 48340 ("Plugin dispose is not called after one-shot run final stop") is a defect of the **V1** host, reported against `opencode-ai@1.18.29`. It is independent of this pin: the V1 host is pinned separately in `.github/opencode-version.txt` (`1.18.30`) and is not a `@opencode/*` package. The V2 pin move neither fixes nor worsens it. It reaches the matrix only through T7, which runs each T1 scenario on both hosts and compares the projected text; the V1 leg is the one it hangs.
