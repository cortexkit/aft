# OpenCode 2 Docker harness

`../../run-opencode2-test.sh` is the local and CI entry point. It reads the pinned GA V2 version from the existing load-matrix source, builds the checkout binary and plugin tarball in Docker, verifies producer-backed executable provenance, validates all registrations, and runs the selected matrix.

The harness keeps its own disk bounded, because nothing else does. The image is tagged with a key derived from the inputs that produced it (checkout SHA, both pinned host versions, and the binary's own producer sidecar), so a re-run lands on the tag it used last time and a changed input lands on a new one — each build replaces its predecessor instead of joining it. The build still decides what is in the image: an uncommitted edit does not move the key, and does not need to, because the tag simply follows whatever the build produced. Every image the script builds carries the `org.cortexkit.aft-e2e=opencode2` label, and on exit — including a killed run — it removes the other tags in its own repository and any labelled image a rebuild left untagged, never forcibly, so an image another run still has a container on is left alone. The steady state is one harness image; images built before the label existed are not recognisable as the harness's own and have to be removed once by hand. Forensics go to the bind-mounted artifact root rather than a named volume, and each run keeps the newest `AFT_E2E_ARTIFACT_RETAIN` run roots (three by default, its own included): roots beyond that quota are removed oldest first, except one written to within the last hour, which belongs to a run that may still be going. A run root is a few gigabytes — every scenario keeps its own project tree and plugin install — so the quota is what stands between a laptop and a full disk, and `AFT_E2E_ARTIFACT_RETAIN=1` is the setting for a box that is already short.

Tool slices add `registration.json`, `registration.ts`, or `*.scenario.json` below `../scenarios/<tool>/`. The loader discovers these files recursively; harness changes are not needed. Optional `*.extension.ts` files may implement `HarnessExtension` for slice-owned validation and lifecycle assertions. The JSON shapes are documented by `registration.schema.json` and `matrix.schema.json`.

Every scenario gets private `HOME`, `TMPDIR`, and `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME`, `XDG_CACHE_HOME`, and `XDG_RUNTIME_DIR` roots. Shared-server scenarios start their host with `serve --service`, so it publishes a registration under the scenario's own `XDG_STATE_HOME`; that registration is both where the harness reads the server password and the only thing the plugin's service discovery looks at. The matrix uses `AFT_E2E_CONCURRENCY` workers (default `4`), while each scenario keeps its own server and per-row timeout. Reports and forensic paths are emitted in scenario-id order. Forensics remain under `AFT_E2E_ARTIFACT_ROOT`. Use `AFT_E2E_SCENARIO=<tool>/<trajectory>` to run one parent row.

A permission scenario declares its operation, the paths it gates, and how the prompt is answered under `metadata.permission`. The harness turns that into an ordered ruleset and installs it on the host session with `PATCH /api/session/{id}` before the first scripted response, because the session ruleset is the one channel the plugin reads and the host evaluates the same rules when the plugin asks it to raise a prompt.

A scenario failure is recorded and the run continues; the report renders every row in scope and ends with the four row counts and the scenario counts. Only run-level preconditions (executable provenance, the harness control suite, input validation, contract loading) end a run before it can report. A failure flagged unsuppressible is a harness-integrity breach and is never excused by a row's expected-failure label. Both host generations are started with `--print-logs`, so a host that dies before serving a turn still explains itself: without it the whole account is one opaque `UnknownError` line on stdout and an empty `host-stderr.log`. A host that runs out its row timeout without answering a single scripted turn fails as `host_startup_stall` rather than `host_failed`, and states how far it got — turns served, model requests received — so a reader can tell a start that never got going from a failure in the tool the row is about. The name says where the run stopped, not whose fault it was: a plugin that hangs while registering stalls a start too, and the forensics beside the row are what tell those apart.

A row may also declare a `verdict_exclusions` entry for one trajectory. That is not an expected-failure label: a label claims the row fails, so a row that passes carrying one is reported as a failure, while an exclusion claims nothing about the outcome and only takes one named thing out of the judgement. Only the subjects the harness implements may be named, on the trajectories where it applies them, each with a reason and with the evidence its subject rests on: a defect cites the upstream issue, and deliberate host behaviour cites a captured reading of the host's own code instead, because there is no report to follow for something the host means to do. The report prints the declaration on the row and prints which exclusion a run actually used beside the scenario's result, so an exclusion is never silent. Two subjects exist today, both on T7:

- `v1_host_process_exit`: the pinned V1 host serves a whole scenario and then never terminates inside a git repository, which every scenario project is, so its exit status and the kill that ends it are left out. Everything else the leg has to do still decides the row, and the exclusion only applies to a leg that served the whole scenario: one still mid-scenario when its time ran out fails on that ending, rather than passing the ending over and failing later on the tool result it never delivered. Because the exit of a served leg is not judged, the harness also stops waiting for it: once the mock has answered the scenario's last scripted turn the leg gets a five-second settling window — enough for a host that does mean to exit to be recorded as having exited — and is then stopped, instead of holding the row open for its full timeout. A leg that never serves settles nothing and still runs out its own timeout.
- `v1_host_edit_family_gate`: the pinned V1 host chooses between `apply_patch` and `edit`/`write` from the model id, inside its own tool registry and before any plugin is consulted, so the mock model the harness drives can never be offered `apply_patch`. The V1 leg of such a row is left out along with the cross-host comparison, and the V2 leg decides the row on its own. The gate is cited by `contract/host1-edit-family-gate.json`, whose captured fragments are read back out of the installed V1 executable on every run that has such a row: a host that no longer contains them ends the run instead of letting the reason go stale.

The contract-owning slice places transcript-backed CLI, provider-config, and schema-rejection contracts under `../contract/`; missing contracts fail validation. A T7 row also runs the V1 host, which takes a different provider shape under a different `opencode.json` key, so it has its own captured observation in `host1-provider-config.json`; the key each host was observed to accept is read back off that file's `opencode_json`. A T7 row compares the two hosts' tool results through its scenario's projection, and `matrix/parity-allowlist.json` names any projected field the two hosts are allowed to differ on, with a reason. An allowlist that covers every field a row projects is refused: that row would compare nothing and report a pass. Text a host wraps around the tool's own result — a completion reminder one generation appends inside the result and the other delivers as its own message — is projected away by an `ignore` rule instead, so the row still compares the outcome the tool reported; allowlisting the outcome field would have left the row comparing nothing. Provider contracts may use `{{AIMOCK_BASE_URL}}` in the captured provider object, which each scenario replaces with its private server URL. Set `AFT_OPENCODE2_SCHEMA_OBSERVATION=1` to run the internal pinned-host schema probe without crediting coverage. If provider setup prevents that probe, its pinned rejection transcript remains a contract observation rather than being treated as coverage.
